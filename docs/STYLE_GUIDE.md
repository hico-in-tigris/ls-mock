# LocalSuccess プロジェクト固有ルール

## 1. このドキュメントの目的

- このプロジェクトで開発・リファクタリングを行う際の「共通ルールブック」とすること
- AIツール（例：Cursor）が自動リファクタリングを行う際の前提条件とすること
- 人間メンバーの認識合わせのベースとすること

## 2. 技術スタック概要

### 言語・フレームワーク

- **言語**: JavaScript（ES2020+）
- **フレームワーク**: React 18.2
- **ビルドツール**: Vite 6
- **ルーティング**: React Router DOM 7

### 主なライブラリ・UIフレームワーク

- **状態管理**: TanStack Query (React Query) 5
- **UIライブラリ**: shadcn/ui (new-york style) + Radix UI
- **スタイリング**: Tailwind CSS 3.4
- **フォーム管理**: React Hook Form 7 + Zod 3
- **アニメーション**: Framer Motion 12
- **グラフ**: Recharts 2
- **日付処理**: date-fns 3
- **マークダウン**: react-markdown 9
- **トースト**: Sonner 2

### ビルド／ツールチェーン

- **パッケージマネージャー**: npm
- **リンター**: ESLint 9 (flat config)
- **パスエイリアス**: `@/` → `src/` (Vite設定)
- **データ永続化**: MockDB (localStorageベース)

## 3. コーディングスタイル

### リンター・フォーマッタ

- **ESLint**: 使用中（flat config形式）
  - `@eslint/js` の recommended ルール
  - `eslint-plugin-react` の recommended + jsx-runtime
  - `eslint-plugin-react-hooks` の recommended
  - `react-refresh/only-export-components`: warn（定数エクスポートは許可）
- **Prettier**: 現時点では未導入（将来的に検討）

### 非推奨な書き方

- `any` 型の使用（TypeScript移行時を想定）
- クラスコンポーネントの使用（関数コンポーネント + Hooks を推奨）
- `React.createElement` の直接使用（JSX記法を推奨）
- インラインスタイルの多用（Tailwind CSS を優先）

### 型の扱い方

- 現時点では JavaScript プロジェクトのため、型定義は JSDoc コメントで記述
- 将来的な TypeScript 移行を想定し、型安全性を意識したコードを書く
- `@param` と `@returns` を活用して関数の型情報を明示

### その他のスタイルルール

- **デフォルトエクスポート**: ページコンポーネントと主要コンポーネントはデフォルトエクスポートを使用
- **命名**: コンポーネント名は PascalCase、ファイル名はコンポーネント名と一致させる
- **インポート順序**: 
  1. React / React DOM
  2. 外部ライブラリ（@tanstack/react-query, react-router-dom など）
  3. 内部モジュール（@/components, @/hooks, @/lib など）
  4. 相対パスインポート
  5. CSS / スタイルファイル

## 4. UIコンポーネント／デザインルール

> **重要**: 詳細なUIデザインガイドラインは [UI_GUIDELINES.md](./UI_GUIDELINES.md) を参照してください。

### shadcn/ui の基本方針

- **スタイル**: new-york style を使用
- **コンポーネント配置**: `src/components/ui/` 配下
- **カスタマイズ**: shadcn/ui コンポーネントは直接編集可能（コピー&ペースト方式）
- **追加コンポーネント**: `npx shadcn@latest add [component]` で追加

### LocalSuccess UIガイドライン

プロダクト全体のUI統一を目的とした軽量デザインシステムが定義されています：

- **デザイン原則**: Calm & Clarity, Flow First, Consistency, Friendly Minimal
- **カラーパレット**: 低彩度のグリーン/アースカラーを基調
- **タイポグラフィ**: 明確な階層構造
- **コンポーネント指針**: LSPageLayout, LSSection, LSCard, LSListItem など
- **ページテンプレート**: 統一されたページ構造

詳細は [UI_GUIDELINES.md](./UI_GUIDELINES.md) を参照してください。

### コンポーネントのレイヤー分け

1. **UIコンポーネント** (`src/components/ui/`)
   - shadcn/ui 由来の基本コンポーネント
   - 再利用可能な汎用コンポーネント（例: `StatsCard.jsx`）
   - スタイルのみを持つプレゼンテーショナルコンポーネント

2. **機能別コンポーネント** (`src/components/[feature]/`)
   - 特定の機能領域に特化したコンポーネント
   - 例: `actions/`, `dashboard/`, `people/`, `thought/` など
   - ビジネスロジックを含む場合がある

3. **ページコンポーネント** (`src/pages/`)
   - ルーティングに対応するトップレベルのコンポーネント
   - データフェッチングとレイアウトを担当
   - 機能別コンポーネントを組み合わせて構成

### Tailwind CSS の使い方方針

- **ユーティリティファースト**: インラインクラスでスタイリング
- **カスタムクラス**: `cn()` 関数（`@/lib/utils`）で条件付きクラスを結合
- **カラーパレット**: shadcn/ui の CSS 変数ベースのカラーシステムを使用
- **レスポンシブ**: モバイルファースト（`sm:`, `lg:` などのブレークポイント）
- **ダークモード**: 対応済み（`darkMode: ["class"]`）

### 共通レイアウト／共通コンポーネント

- **レイアウト**: `src/pages/Layout.jsx` で全ページ共通のレイアウトを提供
- **ナビゲーション**: Layout 内にサイドバーとして実装
- **共通UI**: `src/components/ui/` に配置
- **EmptyState**: `src/components/ui/EmptyState.jsx` を空状態表示に使用

## 5. ディレクトリ構成と責務

```
src/
├── api/              # API クライアント層
│   ├── apiClient.js      # MockDBクライアント（Base44 SDK互換）
│   ├── entities.js       # エンティティエクスポート
│   ├── integrations.js   # 統合機能エクスポート
│   └── mockDB/           # MockDB実装（localStorageベース）
├── components/       # React コンポーネント
│   ├── [feature]/        # 機能別コンポーネント（actions, dashboard, people など）
│   └── ui/               # 共通UIコンポーネント（shadcn/ui）
├── hooks/            # カスタムフック
├── lib/              # ライブラリ・ユーティリティ関数
├── pages/            # ページコンポーネント（ルーティング対応）
├── utils/            # ヘルパー関数
└── index.css         # グローバルスタイル
```

### 各ディレクトリの責務

#### `src/api/`

- **責務**: データフェッチングとAPI通信
- **配置するもの**: 
  - API クライアント実装
  - エンティティ操作のラッパー
  - 統合機能（AI連携など）
- **配置しないもの**: 
  - ビジネスロジック（hooks やコンポーネントに配置）
  - UI コンポーネント

#### `src/components/`

- **責務**: 再利用可能なUIコンポーネント
- **配置するもの**: 
  - 機能別コンポーネント（`[feature]/` 配下）
  - 共通UIコンポーネント（`ui/` 配下）
- **配置しないもの**: 
  - ページコンポーネント（`pages/` に配置）
  - ルーティング設定

#### `src/hooks/`

- **責務**: カスタムフック（ロジックの再利用）
- **配置するもの**: 
  - データフェッチングロジック（TanStack Query の useQuery/useMutation ラッパー）
  - 状態管理ロジック
  - 副作用処理
- **命名規則**: `useXxx.js` 形式

#### `src/lib/`

- **責務**: 汎用的なユーティリティ関数
- **配置するもの**: 
  - `cn()` 関数（クラス名結合）
  - その他の汎用ヘルパー関数
- **配置しないもの**: 
  - 機能固有のロジック

#### `src/pages/`

- **責務**: ルーティングに対応するページコンポーネント
- **配置するもの**: 
  - ページコンポーネント（PascalCase命名）
  - ルーティング設定（`index.jsx`）
- **配置しないもの**: 
  - 細かいUIコンポーネント（`components/` に配置）

#### `src/utils/`

- **責務**: アプリケーション固有のヘルパー関数
- **配置するもの**: 
  - ページURL生成関数など
  - アプリケーション固有の変換処理

## 6. ファイル分割の目安

### 1ファイルあたりの行数

- **推奨**: 300行以下
- **警告**: 300-500行（分割を検討）
- **原則NG**: 500行超（必ず分割）

### 分割時の考え方

1. **責務で分割**: 1つのコンポーネントが複数の責務を持つ場合、機能ごとに分割
2. **ロジックとUIで分割**: 
   - データフェッチングロジック → `hooks/useXxx.js`
   - プレゼンテーション → コンポーネントファイル
3. **再利用性で分割**: 複数箇所で使われる部分は独立したコンポーネント/フックに抽出

### 大きくなりがちな典型ファイルへの方針

#### ページコンポーネント（`pages/*.jsx`）

- データフェッチングは `hooks/useXxx.js` に分離
- 複雑なUI部分は機能別コンポーネント（`components/[feature]/`）に分離
- ページコンポーネントは「組み立て」のみを担当

#### レイアウトコンポーネント（`pages/Layout.jsx`）

- ナビゲーション設定は定数として分離可能
- モバイル/デスクトップの切り替えロジックは保持

## 7. 命名規則

### 7.1 コンポーネント

- **命名ルール**: PascalCase
  - 例: `PeopleCard`, `StatsCard`, `TodayActions`
- **ファイル名**: コンポーネント名と一致（`.jsx` 拡張子）
  - 例: `PeopleCard.jsx`, `StatsCard.jsx`
- **デフォルトエクスポート**: ページコンポーネントと主要コンポーネントはデフォルトエクスポート
- **命名パターン**:
  - 単一アイテム: `XxxCard`, `XxxForm`, `XxxDialog`
  - リスト: `XxxList`（内部で `XxxCard` を使用）
  - ページ: `Xxx`（例: `Dashboard`, `People`）

### 7.2 Hooks

- **命名ルール**: `useXxx` 形式（camelCase）
  - 例: `useHypothesisDetail`, `useHypothesisHandlers`
- **ファイル名**: `useXxx.js`（`.js` 拡張子、JSXを含む場合は `.jsx`）
- **配置場所**: 
  - グローバルに使用されるフック: `src/hooks/`
  - 機能固有のフック: 将来的に `src/hooks/[feature]/` への分割を検討

### 7.3 ページ／ルーティング

- **ページコンポーネント**: PascalCase（例: `Dashboard.jsx`, `People.jsx`）
- **ルーティング**: React Router DOM を使用
  - パスは `/Dashboard`, `/People` など（PascalCase）
  - 動的ルートは `/people/:id` 形式
- **ページコンポーネントの責務**:
  - データフェッチング（TanStack Query の useQuery/useMutation）
  - レイアウト構造の定義
  - 子コンポーネントへの props 受け渡し
  - ビジネスロジックは hooks に分離を推奨

### 7.4 型・モデル

- **現時点**: JavaScript プロジェクトのため、型定義は JSDoc で記述
- **命名規則**: 
  - エンティティ: PascalCase（例: `Person`, `Project`, `Hypothesis`）
  - DTO: エンティティ名と同一
- **置き場所**: 
  - API レスポンス型: `src/api/entities.js` に JSDoc で記述
  - UI用型: コンポーネントファイル内で JSDoc で記述

### 7.5 その他の命名規則

- **定数**: UPPER_SNAKE_CASE（例: `PAGES`, `localSuccessNav`）
- **変数・関数**: camelCase
- **CSS クラス**: Tailwind CSS のユーティリティクラスを使用

## 8. リファクタリングポリシー（AIが守るべきこと）

### 外部仕様・画面挙動・APIインターフェースを変えない

- **原則**: リファクタリングは「動作を変えずにコードを改善する」こと
- **変更禁止**:
  - 画面の見た目・レイアウト（意図的な改善を除く）
  - API の呼び出し方法・パラメータ
  - ルーティング設定
  - データ構造（エンティティのフィールド名など）

### 変更の優先順位

1. **動作の維持**（最優先）
   - 既存の機能が正常に動作することを最優先
   - リファクタリング後に必ず動作確認
2. **可読性**
   - コードの意図が明確になるようにリファクタリング
   - コメントや JSDoc の追加も可読性向上に含む
3. **拡張性**
   - 将来的な機能追加を考慮した構造
   - ただし、過度な抽象化は避ける
4. **パフォーマンス**
   - 明らかなパフォーマンス問題がある場合のみ最適化
   - 早期最適化は避ける

### 大きな構造変更を行う場合の原則

- **Plan に明記**: 大きな構造変更（ディレクトリ移動、アーキテクチャ変更など）は事前に計画を立てる
- **段階的実施**: 一度に大きな変更を行わず、小さなステップに分割
- **動作確認**: 各ステップ後に動作確認を実施

### 定期リファクタリング時のチェック項目

1. **大きすぎるファイルの分割**
   - 500行超のファイルを特定し、分割計画を立てる
   - 300行超のファイルも分割を検討
2. **繰り返し出てくるコードのコンポーネント化／共通化**
   - 同じパターンのコードが3回以上出現する場合は共通化を検討
   - ただし、過度な抽象化は避ける
3. **新しいルールの適用状況の確認**
   - このドキュメントのルールが守られているか確認
   - 特に命名規則とディレクトリ構成
4. **ファイル名・ディレクトリ構成の見直し**
   - 命名規則に従っているか確認
   - ディレクトリ構成が機能別に整理されているか確認
5. **不要コード・不要ファイルの削除**
   - 使用されていないコンポーネント・関数・ファイルを削除
   - コメントアウトされたコードは削除（Git履歴で復元可能）

### リファクタリング時の具体的な指針

- **コンポーネント分割**: 
  - 1つのコンポーネントが複数の責務を持つ場合、機能ごとに分割
  - データフェッチングロジックは hooks に分離
- **命名の統一**: 
  - 同じ概念には同じ名前を使用
  - 略語は避け、明確な名前を選択
- **インポートの整理**: 
  - 未使用のインポートを削除
  - インポート順序を統一（React → 外部ライブラリ → 内部モジュール → 相対パス）
